# 向量存储后端对比实验

对应《技术方案》§12 与《二期实施说明》阶段 9a / 9b。

## 它回答什么问题

> **为什么这个项目用 pgvector？**

这个问题在面试里几乎一定会被追问。「RAG 项目一般都这么做」不是答案；
「我实测过三种后端，在 X 规模下 A 更快且召回率 100%，到 Y 规模才出现拐点」才是。

本实验就是为了产出这个答案。

## 对比对象

| 后端 | 说明 |
|---|---|
| `numpy` | 内存矩阵乘法，暴力全扫。**精确**，作为 Recall 的 ground truth |
| `pg-seq` | pgvector 顺序扫描（`enable_indexscan=off`）。精确，但走数据库 |
| `pg-hnsw` | pgvector + HNSW 索引。**近似**，用召回率衡量它漏了多少 |

指标：P50 / P95 检索延迟、Recall@k、内存/存储占用（两个后端口径不同，见文末）。

## 准备

```bash
cd backend
conda activate blog

```

数据库需处于运行状态（`docker compose -f docker-compose.dev.yml up -d`），


## 两条设计上的硬约束

### N8 · 合成数据必须以真实向量为基底

`datagen.synthesize()` 的做法是：随机取一条真实向量 → 叠加小幅高斯扰动 → 重新 L2 归一化。

**绝不使用 `np.random.randn` 造向量。** 原因：

1024 维空间中，独立随机向量几乎两两正交 —— 任意两条的余弦相似度都集中在 0 附近，
彼此距离几乎相等（高维空间的「距离集中」现象）。而 HNSW 的工作原理正是利用真实
embedding 的**聚类结构**建立近邻图：语义相近的向量扎堆，图上跳几步就能找到邻居。

用随机向量测 HNSW，等于让它在一个没有聚类结构的空间里找近邻 —— 召回率会显著偏低，
**而这个数字看起来完全正常**，不报错、不异常，你会得出「HNSW 召回率很差」的错误结论，
并且完全找不到原因。

因此真实样本少于 `MIN_REAL_SAMPLES`（50）时，`synthesize()` **直接抛
`InsufficientRealData` 拒绝运行**，不提供任何降级路径。这条防线写在代码里，
不是写在注释里。

### N9 · 可复现

固定随机种子（`SEED=42`）、固定查询集构造方式、结果 JSON 中记录完整运行环境
（Python / 平台 / numpy 版本 / embedding 模型与维度 / top_k / 种子 / 块数）。

## 结论

### 实测数据

环境：Windows 11 / Python 3.12 / PostgreSQL 16 + pgvector 0.8.6（Docker，本机）
语料：68 个真实块为基底，扰动重采样扩充；查询集 20 条，种子 42。

**2000 块**

| 后端 | P50 (ms) | P95 (ms) | Recall@10 | 内存/存储 (MB) | 实际扫描 |
|---|---:|---:|---:|---:|---|
| numpy | 1.34 | 1.93 | 1.0000 | 7.8 | 内存全扫 |
| pg-seq | 17.23 | 18.71 | 1.0000 | 29.4 | 顺序扫描 |
| pg-hnsw | 5.68 | 6.76 | 1.0000 | 29.4 | 索引扫描(HNSW) |

**20000 块**

| 后端 | P50 (ms) | P95 (ms) | Recall@10 | 内存/存储 (MB) | 实际扫描 |
|---|---:|---:|---:|---:|---|
| numpy | 27.64 | 29.45 | 1.0000 | 78.1 | 内存全扫 |
| pg-seq | 755.43 | 845.64 | 1.0000 | 292.0 | 顺序扫描 |
| pg-hnsw | 64.53 | 130.40 | 0.9600 | 292.0 | 索引扫描(HNSW) |

### 读出来的三件事

**1. HNSW 的收益拐点在千级，代价到万级才出现。**
2000 块时 HNSW 比顺序扫描快 3 倍，且召回率仍是 1.0 —— 白赚的。
到 20000 块，顺序扫描退化成 755 ms（已经不可用），HNSW 只用 64.5 ms，快 11.7 倍，
代价是召回率掉到 0.96 —— top-10 里平均漏掉 0.4 条。
**这个 4% 就是「近似」两个字的价格**，它在小规模下完全看不见。

**2. numpy 快，但快的是本机进程内调用，不是算法。**
20000 块下 numpy 27.6 ms vs pg-hnsw 64.5 ms，看着 numpy 赢；
但 numpy 是暴力全扫，复杂度 O(n)，20 万块时它会线性劣化到 280 ms，
而 HNSW 是 O(log n)，几乎不动。
numpy 当下的优势来自「省掉一次数据库往返」，规模一上去就被算法复杂度吃掉。

**3. 存储代价：pgvector 约为 numpy 矩阵的 3.7 倍。**
78.1 MB vs 292 MB。差额不是向量本身（两边都是 1024 维 float32），
而是 PG 还存了块正文、上下文前缀、行头开销和 HNSW 的图结构。
换来的是持久化、事务、崩溃恢复和 SQL 过滤（按标签 / 目录 / 单篇筛选），
这些 numpy 版本一个都没有。

### 所以为什么选 pgvector

- 本项目预期规模在**千级块**，正处在 HNSW「提速 3 倍且零召回损失」的甜区
- 检索需要按标签、目录、单篇过滤 —— 这是 SQL 的主场，numpy 版要自己维护倒排
- 数据要持久化、要能崩溃恢复，不能每次重启重算 embedding（那是真金白银的 API 调用）
- numpy 后端保留下来，作用是**当 ground truth**：一致性校验能立刻发现 pgvector 侧
  的查询写错、索引建错、维度对不上

## 踩过的两个坑（都会输出「看着正常」的错误数字）

### 坑一 · 合成数据没进数据库

早先的 `run_bench` 把扩充后的语料喂给了 numpy，却让 pgvector 继续查库里那 68 行真实数据。
两侧面对的语料根本不是同一份，于是：

- Recall 算的是「2000 条里的 top-10」有多少落在「68 条里的 top-10」里 —— 得到 **0.805**
- 这个数字看着像个正常的近似召回率，**不报错、不异常**
- 报告里 `pg-seq` 那行写着 `n_chunks: 2000`，实际只有 68 行；延迟也是 68 行的延迟
- 更隐蔽的是：`pg-seq` 是顺序扫描，理论上**必然**精确、Recall 必须是 1.0。
  它出现 0.805 本身就是矛盾，这是发现问题的线索

修复方式：把语料装进独立 schema `bench_tmp`（结构 `LIKE public.chunks INCLUDING ALL`，
连 HNSW 索引一起复制），把会话 `search_path` 指过去，跑完 `DROP SCHEMA ... CASCADE`。
**生产表 `public.chunks` 全程只读不写**，不会被合成数据污染。

### 坑二 · `enable_indexscan = on` 不等于走了索引

它只是**允许**规划器用索引，不是强制。小规模下规划器算出顺序扫描更便宜，
于是 `pg-hnsw` 那一行其实压根没碰 HNSW —— 两行数字几乎一样，看着像
「HNSW 没什么用」。

修复方式：每轮跑之前用 `EXPLAIN` 读一次实际执行计划，把 `顺序扫描` /
`索引扫描(HNSW)` 打进结果表。不猜，直接看。

顺带：装载后必须 `ANALYZE`，否则规划器拿的是默认行数估计，选择依据是错的。

## 另外修掉的一个缺陷

`numpy_store.py` 只有 `_save()` 没有 `_load()`，且 `get_store()` 每次调用都新建实例，
导致该后端**实例化后 `_chunks` 恒为空、`search()` 永远返回空列表**，且不报任何错。
因为 `VECTOR_BACKEND` 一直是 `pgvector`，这个后端从未被真正执行过，
一致性校验第一次跑就把它暴露了出来。

## 指标口径说明

「内存/存储」一列**两个后端不是同一种东西**，不能直接比大小：

- `numpy` 报的是常驻向量矩阵本身的字节数（`ndarray.nbytes`）
- `pgvector` 报的是 `pg_total_relation_size`，即表 + 全部索引在 PG 里的占用

早先这里报的是**进程 RSS**，那是错的：三个后端跑在同一个进程里、按顺序执行，
numpy 的矩阵一旦载入就不释放，测 pgvector 时读到的 RSS 里仍然含着那块矩阵，
于是三行数字几乎一样，看着像「pgvector 也吃了 900 MB」——
而 pgvector 的内存其实在 PostgreSQL 服务端进程里，根本不在本进程。
