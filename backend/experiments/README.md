# 向量存储后端对比实验

对应《技术方案》§12 与《二期实施说明》阶段 9a / 9b。

## 它回答什么问题

> **为什么这个项目用 pgvector？**

这个问题在面试里几乎一定会被追问。「RAG 项目一般都这么做」不是答案；
「我实测过三种后端，在 X 规模下 A 更快且召回率 100%，到 Y 规模才出现拐点」才是。

本实验就是为了产出这个答案。

## 对比对象

| 后端 | 说明 |
|---|---|
| `numpy` | 内存矩阵乘法，暴力全扫。**精确**，作为 Recall 的 ground truth |
| `pg-seq` | pgvector 顺序扫描（`enable_indexscan=off`）。精确，但走数据库 |
| `pg-hnsw` | pgvector + HNSW 索引。**近似**，用召回率衡量它漏了多少 |

指标：P50 / P95 检索延迟、Recall@k、进程常驻内存。

## 两条设计上的硬约束

### N8 · 合成数据必须以真实向量为基底

`datagen.synthesize()` 的做法是：随机取一条真实向量 → 叠加小幅高斯扰动 → 重新 L2 归一化。

**绝不使用 `np.random.randn` 造向量。** 原因：

1024 维空间中，独立随机向量几乎两两正交 —— 任意两条的余弦相似度都集中在 0 附近，
彼此距离几乎相等（高维空间的「距离集中」现象）。而 HNSW 的工作原理正是利用真实
embedding 的**聚类结构**建立近邻图：语义相近的向量扎堆，图上跳几步就能找到邻居。

用随机向量测 HNSW，等于让它在一个没有聚类结构的空间里找近邻 —— 召回率会显著偏低，
**而这个数字看起来完全正常**，不报错、不异常，你会得出「HNSW 召回率很差」的错误结论，
并且完全找不到原因。

因此真实样本少于 `MIN_REAL_SAMPLES`（50）时，`synthesize()` **直接抛
`InsufficientRealData` 拒绝运行**，不提供任何降级路径。这条防线写在代码里，
不是写在注释里。

### N9 · 可复现

固定随机种子（`SEED=42`）、固定查询集构造方式、结果 JSON 中记录完整运行环境
（Python / 平台 / numpy 版本 / embedding 模型与维度 / top_k / 种子 / 块数）。

### 阶段 9b（T9-6 ~ T9-7）⬜ 待真实内容

当前知识库仅 **15 个块**。这个规模下的实测数据是这样的：

| 后端 | 块数 | P50 (ms) | P95 (ms) | Recall@10 | RSS (MB) |
|---|---:|---:|---:|---:|---:|
| numpy | 15 | 0.045 | 0.053 | 1.0000 | 81.4 |
| pg-seq | 15 | 5.945 | 6.799 | 1.0000 | 81.9 |
| pg-hnsw | 15 | 5.536 | 6.337 | 1.0000 | 82.0 |

**这组数字不能作为结论**，原因有三：

1. **Recall 三个都是 1.0 是必然的** —— 总共 15 个块，取 top-10 等于取走三分之二，
   HNSW 想漏都难。近似检索的代价在这个规模下根本不会显现。
2. **pgvector 的 5～6 ms 几乎全是数据库往返开销**，不是检索本身的耗时。
   numpy 快百倍只说明「省掉一次网络往返」，不说明算法优劣。
3. **HNSW 与顺序扫描几乎无差** —— 15 行数据上查询计划器大概率根本没走索引。

要得到有意义的结论，需要**数百到数千个真实块**。届时才能回答：
HNSW 的收益拐点在哪、召回率损失多少、内存代价多大。
