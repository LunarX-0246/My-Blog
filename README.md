# My Blog · 个人技术博客与 RAG 知识库问答系统

> 记录技术，也让知识可以被提问。

一个自建的个人技术博客。除了写文章、传资料，它还能就站内内容回答提问 ——
**每个回答都必须给出可点击、可验证的原文出处**，而不是让模型自由发挥。

## 这个项目在解决什么问题

一个写了几十篇技术文章、存了几十份资料的博客，读者想找某个具体结论时只能靠翻。
接一个通用大模型对话框也没用 —— 它回答的是自己的通用知识，不是博主写过的东西。

所以这个系统的核心不是"能聊天"，而是**回答必须来自站内内容，并且能被核对**：

- 检索不到就明确说没有，**严禁用模型的通用知识补足**
- 每条论断带引用角标，点击跳转到原文的**具体位置**（文章跳标题锚点，PDF 跳对应页码）
- 界面明确标注本次回答**是否**检索了知识库

## 核心特性

### 检索不是简单的向量 Top-K

- **混合检索**：语义检索 + BM25 关键词检索，用 RRF 融合排序
- 技术内容里大量是函数名、报错信息、参数名这类**精确词**，纯语义检索容易失准，BM25 正好补上
- BM25 自行实现（含倒排索引与中文分词降级），未使用检索框架

### 按需检索，而非每问必检

检索被设计为**模型可调用的工具**，由模型自行判断当前问题需不需要查知识库 ——
闲聊类问题不必浪费一次检索，而这个设计也为后续扩展更多工具（列出文章清单、查看目录结构、按时间筛选）留好了位置。

### 切块保留结构与上下文

- 按 **Markdown 标题层级**切分，而非固定长度滑窗 —— 代码块与表格不会被从中间切碎
- 每个块拼接**上下文前缀**（`文章标题 > 一级标题 > 二级标题`）。
  块脱离原文后，"它"、"这个方法"、"上面提到的"全部失去指代，标题路径是成本最低的语境补偿
- PDF **按页解析**，页码一路保留到块级，这是引用能跳到具体页的前提

### 增量索引

每个块存内容指纹，重新索引时比对指纹，**只对变化的块调用向量化 API**。
改一篇文章通常只有两三个块变化，API 调用量相差一个数量级。

### 向量存储双后端可切换

`pgvector`（生产）与 `numpy` 暴力检索（对照）共用同一套抽象接口，
用于在真实数据上实测两者的延迟、召回率与内存占用差异，产出对比报告。

### 面向 2 GiB 服务器的工程约束

目标运行环境是 2 核 / 2 GiB 的云服务器。
**服务器上不跑任何模型**，全部通过云端 API；数据库参数、容器内存上限、
构建位置（绝不在服务器上执行前端构建）都按这个约束设计。

## 技术栈

| 层 | 选型 |
|---|---|
| 前端 | Next.js 15（App Router）· React 19 · TypeScript · Tailwind CSS |
| 后端 | Python 3.12 · FastAPI · SQLAlchemy 2.0 · Alembic |
| 数据库 | PostgreSQL 16 + pgvector（业务数据与向量一库两用） |
| 大语言模型 | DeepSeek（流式生成） |
| 文本向量化 | 千问 `text-embedding-v3`（1024 维） |
| 文档解析 | PyMuPDF（按页）· markdown-it-py |
| 部署 | Docker Compose · Nginx · Let's Encrypt |

**刻意未引入**：LangChain、FAISS/Chroma/Milvus、Celery/Redis、前端状态管理库。
切块、检索、Agent 循环、上下文压缩全部自行实现。

```
                        访客浏览器
                            │ HTTPS
                            ▼
        ┌───────────────────────────────────────┐
        │              Nginx 网关                │
        │  /api/* → FastAPI   │   /* → Next.js  │
        └───────────────────────────────────────┘
              │                        │
              ▼                        ▼
      ┌──────────────┐  ← SSR 取数 ┌──────────────┐
      │   FastAPI    │             │   Next.js    │
      │ 业务 + RAG   │             │  仅负责渲染   │
      └──────────────┘             └──────────────┘
              │
              ▼
      ┌────────────────────────────┐
      │  PostgreSQL 16 + pgvector  │
      └────────────────────────────┘
              │                    │
              ▼                    ▼
      千问 Embedding        DeepSeek Chat
```

**流式问答由浏览器直连 FastAPI，不经 Node 中转** —— 多一跳会引入缓冲，
让流式输出退化成"转圈很久再整段蹦出来"。

## 本地运行

### 前置要求

| | 版本 |
|---|---|
| Docker Desktop | 4.x |
| Python | 3.12 |
| Node.js | 20+ |

### 步骤

```bash
# 1. 克隆
git clone https://github.com/LunarX-0246/My-Blog.git
cd My-Blog

# 2. 配置环境变量
cp .env.example .env
# 编辑 .env，填入 DEEPSEEK_API_KEY、DASHSCOPE_API_KEY 等

# 3. 启动数据库（PostgreSQL + pgvector）
docker compose -f docker-compose.dev.yml up -d

# 4. 后端
cd backend
pip install -r requirements.txt
alembic upgrade head
uvicorn app.main:app --reload --port 8000

# 5. 前端（另开终端）
cd frontend
npm install
npm run dev
```

访问 http://localhost:3000

> **宿主机端口是 5433 而非 5432**，以避开开发机上可能已存在的 PostgreSQL 实例。
> 容器内部与生产环境仍是 5432。

### 生成管理员密码哈希

```bash
python -c "import bcrypt,getpass; print(bcrypt.hashpw(getpass.getpass('密码: ').encode(), bcrypt.gensalt()).decode())"
```

输入不会回显，输出的哈希填入 `.env` 的 `ADMIN_PASSWORD_HASH`。
系统不提供注册功能，只有这一个账号；密码以 bcrypt 哈希存储，不存明文。

## 目录结构

```
.
├── backend/              FastAPI 后端
│   └── app/
│       ├── api/          路由层
│       ├── rag/          RAG 核心（不依赖 Web 框架，可独立运行）
│       │   ├── parser.py     解析（PDF 按页）
│       │   ├── chunker.py    切块与上下文前缀
│       │   ├── embedder.py   向量化
│       │   ├── bm25.py       关键词检索
│       │   ├── store/        向量存储（pgvector / numpy 双后端）
│       │   ├── retriever.py  混合检索与 RRF 融合
│       │   ├── agent.py      按需检索的工具调用
│       │   ├── memory.py     多轮上下文分层压缩
│       │   └── generator.py  生成与引用标注
│       └── services/     业务逻辑
├── frontend/             Next.js 前端
├── nginx/                生产环境网关配置
├── docker-compose.dev.yml    本机开发：仅数据库
└── docker-compose.yml        生产：全栈编排
```

`rag/` 不依赖 FastAPI，每个模块可独立运行自测 —— 检索质量的调试不应受 Web 层牵制。
