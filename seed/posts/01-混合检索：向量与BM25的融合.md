# 混合检索：向量与 BM25 的融合

做 RAG 时最容易走的一条弯路，是认为「检索 = 把问题变成向量，然后找最近的几个块」。
这条路在演示里跑得通，在真实内容上会持续地、悄无声息地失准。

## 纯向量检索会在哪里失手

向量检索的长处是理解近义表达：问「怎么让模型别乱编」，能召回讲「幻觉抑制」的段落，
哪怕字面一个字都不重合。

但它有一类系统性弱点 —— **精确词**。

技术内容里到处是这种词：函数名 `rrf_fusion`、参数 `chunk_overlap`、
报错信息 `dial tcp: i/o timeout`、库名 `pgvector`。这些词的语义几乎为零，
它们的价值全在「字面一模一样」上。把它们丢进 embedding 模型，
得到的向量和一堆语义相近但字面无关的内容挤在一起，排序就乱了。

我实测过一个典型例子：在一篇讲混合检索的文章里搜 `rrf`，
纯向量检索把「融合排序」「加权打分」这些语义相近的段落排在前面，
而真正含 `rrf` 代码的那一块排到了第七位。

## BM25 补的正是这一块

BM25 是纯粹的关键词打分，公式里三个部分各管一件事：

- **词频 TF**：这个词在文档里出现得多不多
- **逆文档频率 IDF**：这个词在整个语料里罕不罕见 —— 越罕见越有区分度
- **文档长度归一化**：长文档天然更容易命中，要打个折

```python
score(D, Q) = Σ IDF(q) · f(q,D)·(k1+1) / (f(q,D) + k1·(1-b+b·|D|/avgdl))
```

`k1` 控制词频饱和度（常用 1.2~2.0），`b` 控制长度归一化强度（常用 0.75）。

关键在于：**BM25 对 `rrf` 这种罕见词的 IDF 极高**，一击就中。
它不理解语义，但它不需要理解 —— 用户敲出这个词，就是想要字面匹配。

## RRF：怎么把两路结果合起来

两路检索给出的分数不在同一个量纲上（余弦相似度在 0~1，BM25 分数可以是任意正数），
直接加权相加是没有意义的。

**RRF（Reciprocal Rank Fusion）绕开了这个问题：它只看排名，不看分数。**

```python
def rrf_fusion(ranked_lists, k=60, top_k=5):
    scores = defaultdict(float)
    for ranked in ranked_lists:
        for rank, item in enumerate(ranked):
            scores[key(item)] += 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: -x[1])[:top_k]
```

一个块在某一路里排第 1，得 `1/61`；排第 10，得 `1/70`。
**两路都进前列的块，累加后自然浮到最上面**；只有一路捞到的，也不会被完全埋没。

常数 `k` 起平滑作用：k 越大，排名靠前的优势越小，融合越"民主"。60 是论文里的经验值。

## 融合前必须应用同一套过滤

一个容易漏的细节：如果检索带范围限定（比如「只问这篇文章」），
**两路都必须应用同一个过滤条件**。

只在其中一路过滤会出现一种很隐蔽的退化：另一路的结果被过滤掉后，
融合实际上退化成了单路检索 —— 而返回结果看起来完全正常，
你不会发现混合检索已经不工作了。

| 场景 | 向量检索 | BM25 | 融合后 |
|---|---|---|---|
| 语义化提问 | 强 | 弱 | 向量主导，BM25 兜底 |
| 精确术语 | 弱 | 强 | BM25 主导 |
| 两者兼有 | 中 | 中 | 双路加权，最稳 |

## 一个性能上的坑

BM25 需要一个倒排索引。如果每次查询都重新建索引（拉全量文档 + 全量分词），
在几千个块的规模下就是秒级开销 —— 而这发生在 LLM 开始生成之前。

实测数据：500 块 198ms，2000 块 809ms，5000 块 1930ms。

正确做法是**进程内缓存索引，内容变更时失效**。
但要注意缓存的是「全量索引」，带过滤条件的查询在检索后再过滤 ——
如果过滤条件很窄（比如限定单篇文章），全局 top-k 里可能一条都不剩，
这时应该退回到「在候选集上临时建一个小索引」。
