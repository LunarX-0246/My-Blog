# 增量索引：让重复发布不再烧钱

博客内容会被反复修改。改个错别字、补一段说明、调整一处措辞 ——
如果每次保存都把整篇文章重新向量化，API 调用量会以一种毫无必要的方式增长。

## 问题有多大

假设一篇文章切出 20 个块，你在一周内改了 8 次。

| 做法 | 向量化调用次数 |
|---|---|
| 全量重算 | 20 × 8 = **160** |
| 增量索引 | 20（首次）+ 约 2×7 = **34** |

差了将近五倍。而实际情况下，改一次通常只有一两个块真的变了。

## 内容指纹

做法很直接：给每个块算一个内容指纹，重新索引时先比对。

```python
def _fingerprint(context_prefix: str, content: str) -> str:
    """指纹 = sha256(上下文前缀 + 正文)"""
    return hashlib.sha256(
        (context_prefix + "\n" + content).encode("utf-8")
    ).hexdigest()
```

**注意指纹要包含上下文前缀**，不能只算正文。
因为改标题时正文没变，但这个块的语义上下文变了 ——
它的向量应该跟着重算。只算正文的话，改标题不会触发重新向量化，
索引里留的还是旧标题下的语义。

## 三步走

```python
existing = {c.fingerprint: c.embedding for c in 已有的块}

# 1. 只对新增或变化的块调用向量化
to_embed = [c for c in new_chunks if c.fingerprint not in existing]
vecs = embed_batch([c.embed_text for c in to_embed])

# 2. 未变化的块直接复用旧向量
for c in new_chunks:
    emb = new_vecs.get(c.fingerprint) or existing.get(c.fingerprint)

# 3. 原文里已不存在的块，从索引中删除
for fp in existing:
    if fp not in {c.fingerprint for c in new_chunks}:
        delete_chunk(fp)
```

第三步容易漏。删掉一段文字后如果不清理对应的块，
它会继续留在索引里被检索到 —— **AI 会引用一段已经不存在的内容**，
而且点进去发现原文里根本没有。

## 全量重建：一个必须留的后门

增量索引有个致命的盲区：**换 embedding 模型时它会完全失效**。

```
换模型 → 块文本没变 → 指纹没变 → to_embed 为空 → 全部复用旧模型算的向量
```

新旧模型的向量在不同的语义空间里，混在一起检索结果会静默劣化 ——
没有任何报错，只是答得越来越不对。

所以必须有一条**忽略指纹、强制全量重算**的路径。而且这条路径要能在
「服务起不来」的情况下执行 —— 因为启动自检发现模型与索引不一致时会拒绝启动，
这时候你连管理页都进不去：

```
自检拒绝启动 → 想重建索引 → 进不了管理页 → 死循环
```

解法是留一个命令行入口，绕过队列和自检直接同步重建：

```bash
python -m app.services.index_service --rebuild
```

## 崩溃恢复时别把 force 丢了

如果全量重建跑到一半进程崩了，恢复时必须记得**这些任务原本是 force 的**。

把 force 标记只放在内存队列里是不够的 —— 进程一重启就没了，
恢复出来的任务会按增量执行，于是又回到「文本没变→指纹没变→复用旧向量」的老路。

**force 标记要随任务持久化到数据库。**

## 怎么验证它真的生效了

不要只看代码。找一篇已索引的文章，**改一个错别字重新发布**，
然后看索引任务记录：

```
chunk_total = 20
chunk_new   = 1        ← 只重算了 1 块，增量生效
```

如果 `chunk_new == chunk_total`，说明指纹比对根本没起作用 ——
代码可能写了，但某个环节让指纹每次都变（比如前缀里混进了时间戳）。
