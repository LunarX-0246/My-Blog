# 引用溯源：让答案可被核对

一个接在自己内容上的问答系统，相对于直接用通用大模型，
优势只有一条：**答案能被核对**。

这条优势做不实，整个系统就退化成了一个套着自己域名的通用对话框。

## 三件事必须同时做到

### 一、回答只能基于检索内容

这是地基。System Prompt 里必须写死：

```
1. 只使用「参考资料」中的内容作答，禁止使用你自己的通用知识补充或推测。
2. 每个关键论断后标注来源编号，如 [1]、[2]。
3. 如果参考资料不足以回答，直接说明「知识库中没有相关内容」，
   并推荐资料中最接近的 2-3 项，绝不编造。
```

网上大量模板会写成「若资料中没有提及，请结合你的通用知识予以说明」——
**这一句会把整个系统的立足点抽掉**。加了它，访客得到的不再是你的观点，
而是通用模型的回答。

### 二、引用编号必须和来源一一对应

模型输出 `[1]`，前端要能把它映射到一个具体的 URL。

这里有个多轮场景下的坑：如果模型在一轮对话里**调用了两次检索**，
而每次组装参考资料时编号都从 `[1]` 重新开始，模型看到的上下文里
就会出现两组 `[1]`：

```
第 1 次检索返回：        第 2 次检索返回：
  [1] 文章A > 混合检索      [1] 文章B > 增量索引
  [2] 文章A > RRF
```

如果前端拿到的 `sources` 只是最后一次检索的结果，
点 `[1]` 会跳到**错误的来源**。

这比"跳不动"严重得多 —— **它看起来是正常工作的**，
访客不会察觉自己被指向了错误的出处。

正确做法：来源累加不覆盖，编号全局连续，去重后再编号。

```python
start = len(sources) + 1
for c in new_sources:
    if key(c) not in seen:
        seen.add(key(c)); sources.append(c); fresh.append(c)
content = build_context(fresh, start=start)
```

### 三、跳转要落到具体位置

跳到文章顶部不算溯源 —— 访客还得自己在几千字里找。

| 内容 | 跳到哪 | 靠什么 |
|---|---|---|
| 文章 | 对应小节 | 标题锚点 `#rrf-融合` |
| PDF | 对应页 | 解析时记录的页码 |
| Markdown / txt | 对应块 | 块序号锚点 `#chunk-7` |

**锚点算法前后端必须逐字一致**。后端切块时算出的 `#rrf-融合`，
前端渲染标题时也要生成同样的 id，否则跳过去什么都没有。

现成的 slug 库（如 `rehype-slug`）通常用固定算法，
和后端对不上时，与其去迁就它，不如两边各写一份一致的实现。

还要注意**重复标题的去重规则也要一致**：同一篇文章里有两个
`## 说明` 时，如果前端给第二个加了 `-1` 后缀而后端没加，
指向第二节的引用会跳到第一节。

## 界面要说实话

三个状态必须区分清楚：

```
已检索知识库          → 答案有站内内容依据，附来源卡片
查看了文章清单/目录    → 只用了元数据工具，不是内容检索
本次未检索知识库      → 模型判断不需要查
```

第二种最容易被含糊过去。调了 `list_posts` 拿到一串标题，
不等于"检索了知识库"—— 模型并没有读到任何正文。
把它标成已检索，这个信号就脏了。

## PDF 的一个妥协

PDF 阅读器只能跳到页，跳不到段落。所以 PDF 引用的精度天然低于文章。

如果这个精度不够，可以额外提供一个「文本视图」—— 展示解析后的纯文本，
按块渲染、每块带锚点。它同时解决另一个问题：

**访客在原文视图看到的是原始 PDF，AI 读到的是解析后的文本，两者可能对不上。**
解析结果在文字顺序、表格还原、页眉页脚剔除上都可能有差异。
文本视图展示的正是 AI 实际读到的内容，需要逐字核对时切过去看。
