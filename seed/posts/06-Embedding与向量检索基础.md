# Embedding 与向量检索基础

在做检索之前，得先把文字变成向量。这一步的细节做错了，
后面所有的融合排序、重排、Agent 循环都建立在错的基础上。

## 三个容易漏的细节

### 查询侧和文档侧可能不对称

有些 embedding 模型是用**非对称检索**的方式训练的 ——
查询和文档走不同的输入格式。BGE 系列就是典型：官方要求查询侧加一个指令前缀，
文档侧不加。

不加这个前缀，查询向量和文档向量根本不在同一个语义空间里对齐，
**召回质量会明显下滑**。而且这种下滑没有任何报错，
你只会觉得"这个模型不太行"。

用 API 版的 embedding 服务通常不需要操心这个，但要确认一下文档。

### 池化方式要和训练时一致

模型输出的是每个 token 的向量，要合并成一个句向量。
取 `[CLS]` 还是平均池化，**必须和训练时一致**。

BGE 的 `1_Pooling/config.json` 里写死了 `pooling_mode_cls_token=True`，
用平均池化就会得到和训练时不一致的表示。

### L2 归一化

归一化之后，两个向量的**内积就等于余弦相似度**。

这一步带来的好处很实际：检索时一次矩阵乘法就够了，不用逐条算模长。

```python
sims = matrix @ query_vec     # matrix 已归一化，内积即余弦相似度
```

而且它让不同后端的分数可以直接比较 —— numpy 的内积和 pgvector 的
`1 - cosine_distance` 是同一个口径。

## 向量检索到底在算什么

一个 1024 维的向量，就是 1024 个浮点数。
"语义相似"被翻译成了"这两组数字的方向接近"。

```
余弦相似度 = cos(θ) = A·B / (|A|·|B|)
                    = A·B          （归一化后）
```

值域 -1 到 1，越接近 1 越相似。

实测一组数据能帮助建立直觉：

| 查询 | 目标文本 | 相似度 |
|---|---|---|
| 忻州的矿山修复面积 | 忻州相关段落 | 0.809 |
| 忻州的矿山修复面积 | **朔州**相关段落 | **0.667** |
| 忻州的矿山修复面积 | 天气预报 | 0.260 |

注意中间那行：**真正的干扰项比无关内容近得多**。
同类文档的不同版本（忻州 vs 朔州）在向量空间里挨得极近，
光靠相似度排序压不住 —— 这正是需要过滤条件和混合检索的原因。

## 暴力检索 vs 近似索引

在向量库里找最近邻，两种做法：

**暴力全扫**：算出查询向量和所有向量的相似度，排序取前 k。
**精确**，无近似误差。复杂度 O(n)。

**近似索引（HNSW 等）**：建一个近邻图，查询时在图上跳几步找到大致最近的。
**近似**，可能漏。复杂度接近 O(log n)。

拐点在哪？取决于向量数量：

```
几千条    暴力全扫是毫秒级，且 100% 召回 —— 近似索引没有意义
几万条    开始有差距
几十万条  必须用近似索引
```

一个反直觉的点：**小数据量下近似索引可能更慢** ——
图遍历本身有开销，而暴力全扫在几千条上就是一次矩阵乘法。

## 高维空间的一个陷阱

如果你想造合成数据测试检索性能，**千万别用纯随机向量**。

1024 维空间里，独立随机向量几乎两两正交 ——
任意两条的余弦相似度都集中在 0 附近，**彼此距离几乎相等**。
这叫"距离集中"现象。

而 HNSW 的工作原理正是利用真实 embedding 的**聚类结构**：
语义相近的向量扎堆，图上跳几步就能找到邻居。

用随机向量测 HNSW，等于让它在一个没有任何结构的空间里找近邻。
召回率会显著偏低，**而这个数字看起来完全正常**，
你会得出"HNSW 效果很差"的错误结论，并且完全找不到原因。

正确做法是**以真实向量为基底加小幅扰动重采样**，保住聚类结构。
