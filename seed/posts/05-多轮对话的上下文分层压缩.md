# 多轮对话的上下文分层压缩

单轮问答做完之后，加多轮看起来只是「把历史消息 append 上去」。
实际跑几轮就会撞墙。

## 为什么会炸

RAG 的每一轮都会往上下文里塞检索结果，而检索结果是**原文片段**，很长。

一轮问答大致是这样的消息序列：

```
system  : 约束 + 参考资料（5 个块，可能两三千字）
user    : 问题
assistant: 回答
```

第二轮把第一轮整个 append 上去，再加上第二轮自己的参考资料。
**三四轮下来就是上万字**，很快顶到上下文窗口上限。

而且这不只是"会报错"的问题 —— 上下文越长，模型越容易被前面的
无关内容干扰，回答质量反而下降。

## 分层压缩

核心判断是一句话：**刚发生的事需要细节，久远的事只需要结论。**

| 层 | 保留什么 |
|---|---|
| 最近 N 轮 | 完整过程，只把超长的检索结果截断 |
| 更早的轮次 | **只留问题 + 最终答案**，中间的参考资料全丢 |
| 超预算 / 超轮数 | 从最老的轮次开始整轮淘汰 |

为什么这么分：指代消解只依赖最近的上下文。

> 「它的性能怎么样」—— 这个「它」指什么，要看上一轮说了什么
> 「三轮前你提到的那个方案」—— 这种引用极少见，留个结论就够

## 服务端要不要存历史

一个容易做重的决定：**对话历史存哪里**。

服务端存 session 有两个麻烦：进程重启就丢（或者要落库）、
多个 worker 之间不共享、还要处理过期清理。而访客的对话本来就是临时的。

更简单的做法是**服务端无状态**：历史存在访客自己的浏览器里，
每次请求带上来，服务端现场压缩。

```python
history = memory.compress_history(body.history)
```

好处不只是省事：**服务端不存储任何访客的对话内容**，
隐私上也干净 —— 没有需要保护的东西，就没有泄露的风险。

代价是每次请求的 body 大一些。对这个量级完全无所谓。

## 压缩要放在检索之前

顺序容易搞反。压缩的目的是控制送进模型的上下文长度，
所以它必须发生在**组装最终消息之前**：

```
收到请求
  → 压缩历史          ← 这里
  → 判断是否检索
  → 检索
  → 组装 messages（system + 压缩后的历史 + 当前问题）
  → 流式生成
```

如果放在检索之后再压，本轮的参考资料已经拼进去了，压了个寂寞。

## 缓存与多轮的冲突

如果做了问答结果缓存，要注意**多轮对话不能进缓存**。

同一个问题「那它呢」，在不同的对话上下文里含义完全不同。
拿缓存的答案返回会串味 —— 而且这种错误很难被发现，
因为答案本身是通顺的，只是答的不是当前这个问题。

判断很简单：

```python
if not body.history:          # 只缓存无历史的单轮问题
    cache_key = normalize(question)
```

## 怎么验证它工作了

光看代码不行，要实际问：

```
第一轮：混合检索是怎么做的？
第二轮：那它的性能怎么样？      ← 「它」能否正确指向混合检索
第三轮：跟增量索引比呢？        ← 跨轮引用
```

第二轮如果答成了泛泛的性能讨论，说明历史没传对或者被压没了。
