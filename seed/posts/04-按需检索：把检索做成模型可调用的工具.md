# 按需检索：把检索做成模型可调用的工具

大多数 RAG 实现是这样的固定流程：

```
收到问题 → 向量化 → 检索 → 拼 Prompt → 生成
```

每一个问题都走完整条链路。用户说「你好」，系统也一本正经地去检索一遍。

## 每问必检的两个代价

**一是浪费。** 闲聊、问候、「你能干什么」这类问题，检索出来的东西
一条都用不上，但 embedding 调用和检索开销一分不少。

**二是答非所问。** 有些问题检索本身就答不了：

> 「你写过几篇关于 RAG 的？」
> 「最近一个月更新了什么？」
> 「把那篇文章的目录列给我」

这些是**元数据问题**，答案在数据库的字段里，不在文本内容里。
拿去做向量检索，只会召回一堆"提到 RAG"的段落，然后模型开始瞎数。

## 把检索变成一个工具

换个思路：不要把检索当成流程的必经环节，**把它做成模型可以自己决定调不调的工具**。

```python
TOOLS = [{
    "type": "function",
    "function": {
        "name": "search_kb",
        "description": (
            "检索博主的文章与知识库文档。当问题涉及博主写过的内容、"
            "技术观点或站内资料时使用；闲聊、常识性问题不要使用。"
        ),
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string"},
                "scope": {"type": "string", "enum": ["all", "posts", "docs"]},
            },
            "required": ["query"],
        },
    },
}]
```

模型收到问题后先判断：这个要不要查？要查就调 `search_kb`，
不要查就直接回答。**判断逻辑在模型脑子里，不在你的 if-else 里。**

## 一个必须堵上的漏洞

这里有个交界处的陷阱：**模型决定不检索时，它凭什么回答？**

如果不加约束，它会用自己的通用知识作答。于是出现这种情况：

> 访客问「什么是 RAG」→ 模型判定为常识题、不检索 → 用通用知识答了一段

而你的博客里恰好有三篇讲 RAG 的文章。**访客在你的站上拿到了一个通用回答** ——
这正是自建问答相对于直接用通用模型的意义所在，现在意义没了。

所以不检索的路径也必须有约束：

```
你只能回应以下两类内容：
1. 问候、致谢、告别；
2. 关于你自身的元问题（如「你是谁」「你能回答什么」）。

除此之外的任何实质性问题，一律回复「知识库中没有相关内容」，
并建议换个问法。严禁使用你自己的通用知识回答任何实质性问题。
```

## 扩展到多工具

一个工具跑通之后，加工具几乎是零成本的：

| 工具 | 回答什么 |
|---|---|
| `search_kb` | 内容问题 —— 「你怎么看待 X」 |
| `list_posts` | 「你写过几篇关于 X 的」「最近更新了什么」 |
| `get_post_outline` | 「把那篇的目录列出来」 |
| `get_post_section` | 「那篇的第三节讲了什么」 |

后两个组合起来能做**先粗后精**：先检索定位到某一节，再把整节完整取回，
比一次性返回十个碎片更准，也更省 token。

## 元数据工具的新漏洞

加了元数据工具后，那个「用通用知识发挥」的漏洞会换个形式回来：

> 模型调 `list_posts` 拿到一串标题
> → 然后开始点评：「关于 RAG 我写过 3 篇，主要讲的是……」
> → **后半句是它自己编的**

元数据工具返回的是**事实**（标题、日期、数量、目录），
模型只能陈述这些事实，不能据此发挥。这条要写进 Prompt。

## 别把「检索了」这个信号搞脏

界面上要标注本次回答是否用了知识库。但**调用元数据工具不等于检索了知识库**：

```python
used_retrieval = ("search_kb" in used_tools)   # 只认 search_kb
```

如果调了 `list_posts` 也标成「已检索知识库」，这个信号就失真了 ——
访客以为答案有内容依据，实际上模型只看到了一串标题。
