工具调用（Function Calling）速查
================================

一、基本概念
------------
让模型不只是生成文字，而是能够"决定调用某个函数"。
模型本身不执行函数，它只输出「我要调 X，参数是 Y」，
真正的执行由应用层完成，结果再回填给模型。

关键点：控制权始终在应用层。模型只是提议，不是执行。


二、一轮完整的调用
------------------
1. 应用把「工具定义」连同用户消息一起发给模型
2. 模型返回 tool_calls（含函数名与参数 JSON）
3. 应用解析参数，实际执行函数
4. 把执行结果作为 role="tool" 的消息追加回消息列表
5. 再次请求模型，模型基于结果生成最终回答

第 4 步容易写错：结果必须带上对应的 tool_call_id，
否则模型不知道这个结果是哪次调用的返回。


三、工具定义的写法
------------------
{
  "type": "function",
  "function": {
    "name": "get_weather",
    "description": "查询指定城市的当前天气。",
    "parameters": {
      "type": "object",
      "properties": {
        "city": {"type": "string", "description": "城市名，如 北京"},
        "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
      },
      "required": ["city"]
    }
  }
}

description 是模型判断「要不要调这个工具」的唯一依据。
写得含糊，模型就会该调的时候不调、不该调的时候乱调。

好的 description 要写清楚两件事：
  - 这个工具做什么
  - 什么情况下应该用、什么情况下不该用


四、多轮工具循环
----------------
模型可能连续调用多个工具，或者根据前一个工具的结果决定下一步。
所以要写成循环，而不是一次性处理：

    for _ in range(MAX_ROUNDS):
        resp = llm.chat_with_tools(messages, TOOLS)
        if not resp.tool_calls:
            break                    # 模型不再调工具，准备最终回答
        messages.append(assistant_message_with_tool_calls)
        for tc in resp.tool_calls:
            result = execute(tc)
            messages.append({"role": "tool",
                             "tool_call_id": tc.id,
                             "content": result})

MAX_ROUNDS 必须有，否则模型可能陷入反复调用的死循环，
把 token 烧光。经验值 3~5 轮。


五、常见坑
----------
1. 参数是模型生成的 JSON 字符串，可能不合法
   → 一定要 try/except 包住 json.loads，失败时返回可读的错误给模型

2. 工具执行失败不应该让整个请求崩掉
   → 把异常信息作为 tool 消息返回，让模型知道失败了并决定下一步

3. 工具返回内容过长会挤爆上下文
   → 返回前截断，或者只返回摘要 + 一个可深挖的 id

4. 同一轮里多个 tool_calls 要全部执行完再回填
   → 漏掉一个，模型会一直等那个结果

5. 工具返回的是"事实"，模型只能陈述不能发挥
   → 拿到一串标题就开始点评内容，是最常见的越界


六、与 RAG 的结合
-----------------
把「检索」做成一个工具，就实现了按需检索：
模型自行判断这个问题要不要查知识库，而不是每问必检。

好处：闲聊类问题省掉一次检索；
      架构上为后续加更多工具（列清单、查目录、按时间筛）留好了位置。

要注意的是：模型决定不检索时，必须有约束限制它能说什么，
否则它会用通用知识作答 —— 那样自建问答就失去意义了。
