# RAG 讲义要点

课程 week10 的核心内容整理，围绕检索增强生成的完整链路。

## 为什么需要 RAG

大模型的知识截止于训练时点，且无法访问私有数据。微调成本高、更新慢，
而且会引入灾难性遗忘。RAG 把「知识」从模型参数里移到外部存储，
需要时检索出来放进上下文 —— 更新知识只需要更新索引，不用动模型。

代价是每次推理都要多一次检索，且上下文窗口被参考资料占掉一部分。

## 完整链路

```
文档 → 解析 → 切块 → 向量化 → 建索引
                                ↓
问题 → 向量化 → 检索 → 重排 → 拼 Prompt → 生成 → 引用标注
```

每一环都有可以做错的地方，而且大部分错误不会报错，只会让效果变差。

## 解析

不同格式的解析质量差异很大：

| 格式 | 工具 | 注意 |
|---|---|---|
| PDF | PyMuPDF / pdfplumber | 多栏排版容易乱序；表格常常还原不出 |
| Markdown | 直接读 | 结构最好，标题层级现成 |
| Word | python-docx | 格式信息多，噪音也多 |
| HTML | BeautifulSoup | 要先去掉导航、页脚等模板内容 |

PDF 尤其要注意：**逐页解析，保留页码**。拼成一整串之后就找不回来了。

## 切块

两大流派：

**固定长度切分** —— 简单，但会切碎代码、表格、公式。
overlap 参数用来缓解上下文断裂，但治标不治本。

**结构化切分** —— 按文档自身的结构（标题、章节）切。
质量高得多，但依赖文档有结构可用。

无论哪种，都建议给每个块拼上**上下文前缀**（标题路径）。
块脱离原文后代词全部失效，前缀是最便宜的补偿手段。

## 检索策略对比

| 策略 | 优势 | 短板 |
|---|---|---|
| 纯向量 | 理解近义表达 | 精确词、专名、数字弱 |
| 纯 BM25 | 精确匹配强 | 认不出同义词 |
| 混合 + RRF | 两者互补 | 实现复杂一点 |

实验结论：在技术文档语料上，混合检索的召回率明显优于任一单路。
差距主要来自那些含函数名、报错信息的查询。

## 重排（Rerank）

检索返回 top-20 后，用一个交叉编码器对「查询-文档」对逐个打分，重新排序取 top-5。

交叉编码器比双塔模型准，因为它能看到查询和文档的交互；
但它必须逐对计算，无法预先建索引，所以只能用在小候选集上。

本地跑 rerank 模型需要注意资源：`bge-reranker-base` 权重约 1.1 GB，
加载后常驻内存 1.5 GB 左右 —— 在小内存机器上跑不动，
这种场景下应该用 API 版的 rerank 服务，或者干脆不做重排。

## 文档级过滤

一个实测发现：同类文档的不同版本在向量空间里挨得极近。

三份生态修复方案，忻州和朔州两份是同一类文档的不同地市版本，
章节结构和术语几乎照搬。查询「忻州的修复面积」时：

- 对忻州段落相似度 0.809
- 对朔州段落相似度 0.667
- 对无关内容相似度 0.260

**干扰项比无关内容近得多**，光靠相似度排序压不住。
但地名是确定性信号 —— 问题里出现「朔州」就只在那份里检索，
一步把最大的错误来源掐掉。

## 评估

不要凭感觉判断检索好坏。建一个题集，每个问题标注正确答案所在的块，
然后算召回率。

评估时要注意控制变量：**同样的题集、同样的块数、固定的随机种子**。
换了切块策略再比，如果块数从 200 变成 350，那召回率的变化里
有多少来自策略、有多少来自块数变了，就说不清了。
